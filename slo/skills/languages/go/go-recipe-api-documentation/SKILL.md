# Go API Documentation (swaggo/swag + gin-swagger + Redoc)

## Skill summary

- **Name:** `go-recipe-api-documentation`
- **Description:** The Go equivalent of the FastAPI + Redoc documentation setup.
  Go has no runtime schema introspection like FastAPI, so we drive OpenAPI from
  **`swaggo/swag` annotation comments** placed above each handler and on `main`.
  `swag init` parses those comments plus the referenced Go model structs into an
  `openapi`-compatible spec, and **gin-swagger** serves Swagger UI while a static
  handler serves Redoc against the same generated JSON.
- **When to use:** Whenever you add or change a Gin endpoint, introduce a new
  request/response DTO, or need to serve/refresh browsable API docs.
- **Group:** `languages`
- **Kind:** `skill`

## Examples

- "Add Swagger annotations to this Gin handler."
- "Set up OpenAPI docs for my Go service with swag and Redoc."
- "How do I document the response envelope in swaggo?"
- "Generate the OpenAPI spec and serve Swagger UI + Redoc from Gin."
- "Why is my `@Success` model showing as an empty object in Swagger?"
- "Add a CI check that fails when the generated docs are out of date."
- "Document a paginated list endpoint in swag."

## Guidance

**Scope and authority:** Go; read `skills/languages/go/go-conventions/SKILL.md` first. This recipe is a reconciled snapshot of installed guidance, not permission to adopt a dependency. Framework-specific examples apply only to a project already using that stack. Select the test category with `skills/engineering/engineering-testing/SKILL.md`.

Defer to `go-conventions` for all naming, struct-tag, godoc, and
declarative-structure rules — this skill only adds the documentation layer on top.
Handlers themselves stay thin (`go-build-http-handlers`) and the envelope types
come from `go-recipe-api-response-conventions`. Documentation annotations never change
handler behaviour; they are comments the `swag` CLI reads.

### The core mental model — how Go differs from FastAPI

| FastAPI (Python) | Go (swaggo) |
|---|---|
| `response_model=AudioDAO` introspected at runtime | `@Success 200 {object} dto.AudioResponse` annotation parsed at build time |
| `redoc_url=...` in the `FastAPI(...)` constructor | serve Redoc HTML yourself against the generated `doc.json` |
| `custom_openapi()` sets title/version/description | `@title` / `@version` / `@description` annotations on `main` |
| Pydantic model = schema source of truth | Go struct + `json:` tags = schema source of truth |
| Schema generated live on each request | Schema generated by `swag init` into a `docs/` package, compiled in |

Because the spec is generated by a CLI and **compiled into the binary**, the docs
can drift from the code if `swag init` is not re-run. Sections "Generation" and
"CI drift check" exist to prevent exactly that.

## Section 1 — Install and project layout

```bash
# CLI (pin the version in tools; do not rely on a floating global)
go install github.com/swaggo/swag/cmd/swag@latest

# runtime deps for serving
go get github.com/swaggo/gin-swagger
go get github.com/swaggo/files
```

Standard placement, consistent with the layout in `go-conventions`:

```
<service>/
├── cmd/server/main.go        # general API info annotations live here
├── internal/handler/...      # per-handler annotations live above each func
├── internal/.../dto.go       # structs that @Param/@Success/@Failure reference
├── docs/                     # GENERATED by `swag init` — do not hand-edit
│   ├── docs.go
│   ├── swagger.json
│   └── swagger.yaml
└── tools/tools.go            # tool dependency pin (see CI section)
```

`docs/` is generated. Treat it like generated protobuf: it is committed (so `go
build` works without the CLI) but never edited by hand, and CI verifies it is
current.

## Section 2 — General API info (the `main.go` annotations)

This is the Go equivalent of FastAPI's `custom_openapi()` + `api_description`
string. The annotations sit as a comment block immediately above `func main()`.
`@description` supports Markdown — use it to document the response envelope once,
since per-endpoint `@Success` models only describe the `data` payload, not the
full wrapper.

```go
// Package main is the entry point for the accounts service.
package main

// @title           Accounts Service API
// @version         1.0.0
// @description     Account and user management for the platform.
// @description
// @description     ## Response envelope
// @description     Every JSON response is wrapped in a uniform envelope. The
// @description     `@Success`/`@Failure` model on each endpoint documents only
// @description     the `data` field — the wrapper is documented here once:
// @description
// @description     ```json
// @description     {
// @description       "data": { },
// @description       "api_version": "v1.0",
// @description       "errors": { "msg": [], "code": null }
// @description     }
// @description     ```
// @description
// @description     On failure, `errors.code` is a SCREAMING_SNAKE_CASE string and
// @description     `errors.msg` carries human-readable messages.
//
// @termsOfService  https://example.com/terms
// @contact.name    Platform Team
// @contact.email   platform@example.com
// @license.name    Proprietary
//
// @host            api.example.com
// @BasePath        /ac/api/v1
// @schemes         https
//
// @securityDefinitions.apikey BearerAuth
// @in                         header
// @name                       Authorization
// @description                Bearer token: "Bearer {token}"
func main() {
    // ... wire dependencies and start the server; see Section 5.
}
```

Key points:

- `@BasePath /ac/api/v1` mirrors the **service-namespace prefix** rule from
  `go-conventions` — never document a bare `/api/v1`.
- `@securityDefinitions.apikey BearerAuth` declares the auth scheme once; each
  protected handler references it with `@Security BearerAuth`.
- `@version` is the analog of FastAPI's `version="1.0.0"`. Bump it on breaking
  changes; the generation-time stamp goes in CI, not here.

## Section 3 — The response envelope as a documentable type

FastAPI could document `SuccessResponseDAO[T]` generically. `swag` does **not**
resolve Go generics, so you cannot annotate `@Success 200 {object}
SuccessResponse[dto.UserResponse]`. There are two idiomatic ways to make the
envelope show up in the schema. Use approach A by default.

### Approach A (default) — annotate the payload, document the wrapper once

Reference only the payload DTO in `@Success`, and document the wrapper prose in
`@title`'s `@description` (Section 2). This matches the FastAPI convention exactly:
`response_model` described only `data`; the envelope was described once at the top.

```go
// @Success 200 {object} dto.UserResponse "user payload (wrapped in the standard envelope)"
```

The trailing description string is where you remind the reader the payload is
enveloped. This keeps every endpoint's annotation short and avoids duplicating the
wrapper schema on all of them.

### Approach B — concrete non-generic wrapper structs (when you need the full schema)

When a consumer needs Redoc to render the *entire* wrapped shape (e.g. a public
API), define a concrete, non-generic wrapper per payload and reference that. This
is the Go workaround for the missing generic support.

```go
// UserEnvelope documents the full wrapped response for a single user.
// It exists only for swaggo schema generation; handlers still return the
// generic SuccessResponse[dto.UserResponse] from go-recipe-api-response-conventions.
type UserEnvelope struct {
    Data       dto.UserResponse    `json:"data"`
    APIVersion string              `json:"api_version" example:"v1.0"`
    Errors     httpx.ResponseErrors `json:"errors"`
}
```

```go
// @Success 200 {object} docs.UserEnvelope
```

Trade-off: Approach B produces a richer schema but multiplies wrapper types. Reach
for it only on externally consumed endpoints; use Approach A everywhere else.

### The error envelope — document it once, reuse it

Define a single concrete failure struct so every `@Failure` line can reference it.

```go
// ErrorEnvelope is the documented shape of every non-2xx response.
type ErrorEnvelope struct {
    Data       any                  `json:"data"`
    APIVersion string               `json:"api_version" example:"v1.0"`
    Errors     httpx.ResponseErrors `json:"errors"`
}
```

`httpx.ResponseErrors` is the `{ msg []string; code *string }` type from
`go-recipe-api-response-conventions`. Its `example` struct tags drive the sample values
Redoc renders.

## Section 4 — Per-handler annotations

Every annotation is a comment line directly above the handler. Handlers stay thin
(`go-build-http-handlers`); the annotations document, they don't execute.

### 4.1 Anatomy of the tags

| Tag | FastAPI analog | Purpose |
|---|---|---|
| `@Summary` | route `summary` / `name` | one line, < 80 chars |
| `@Description` | route `description` | Markdown body; behaviour, side effects |
| `@Tags` | tag grouping | groups endpoints in the UI (`Accounts`, `Payments`) |
| `@ID` | `name` / operationId | unique operation id across the whole spec |
| `@Accept` / `@Produce` | content types | `json`, `xml`, `octet-stream`, etc. |
| `@Param` | path/query/body params | one line per parameter |
| `@Success` | `response_model` (2xx) | status + type + description |
| `@Failure` | error responses | status + error type + description |
| `@Security` | `Depends(current_user)` | references a `securityDefinitions` scheme |
| `@Router` | the route path + method | `/path [method]` — required |

### 4.2 Single resource (GET) — Good

```go
// GetUser returns a single user by ID.
//
// @Summary      Get a user
// @Description  Returns the user identified by `id`. The payload is wrapped in
// @Description  the standard response envelope (see the API description).
// @Tags         Accounts
// @ID           get-user
// @Produce      json
// @Param        id   path      string  true  "User ID (UUID)"
// @Success      200  {object}  dto.UserResponse  "user payload (enveloped)"
// @Failure      404  {object}  docs.ErrorEnvelope  "user not found"
// @Failure      500  {object}  docs.ErrorEnvelope  "internal error"
// @Security     BearerAuth
// @Router       /users/{id} [get]
func (h *UserHandler) GetUser(c *gin.Context) {
    user, err := h.svc.Execute(c.Request.Context(), c.Param("id"))
    if err != nil {
        httpx.WriteError(c, http.StatusNotFound, err.Error(), "USER_NOT_FOUND")
        return
    }
    httpx.WriteSuccess(c, http.StatusOK, dto.FromUser(user))
}
```

The `@Router` path uses swaggo's `{id}` brace syntax, **not** Gin's `:id`. This is
a common mistake:

```go
// Bad — Gin route syntax in @Router; swag will not match the path param
// @Router /users/:id [get]

// Good — OpenAPI brace syntax; matches the @Param name
// @Router /users/{id} [get]
```

### 4.3 Request body (POST/PUT) — Good

The request DTO is a concrete struct with `json:` + `validate:` tags (the Pydantic
analog is `validator`). `swag` reads the struct to build the request-body schema.

```go
// CreateUser persists a new user.
//
// @Summary      Create a user
// @Description  Creates a user. Fails with 409 if the email is already registered.
// @Tags         Accounts
// @ID           create-user
// @Accept       json
// @Produce      json
// @Param        request  body      dto.CreateUserRequest  true  "user to create"
// @Success      201  {object}  dto.UserResponse    "created user (enveloped)"
// @Failure      400  {object}  docs.ErrorEnvelope  "validation failed"
// @Failure      409  {object}  docs.ErrorEnvelope  "email already registered"
// @Security     BearerAuth
// @Router       /users [post]
func (h *UserHandler) CreateUser(c *gin.Context) {
    var req dto.CreateUserRequest
    if err := c.ShouldBindJSON(&req); err != nil {
        httpx.WriteError(c, http.StatusBadRequest, err.Error(), "INVALID_REQUEST")
        return
    }
    created, err := h.svc.Execute(c.Request.Context(), req)
    if err != nil {
        httpx.WriteError(c, http.StatusConflict, err.Error(), "EMAIL_CONFLICT")
        return
    }
    httpx.WriteSuccess(c, http.StatusCreated, dto.FromUser(created))
}
```

The DTO — its struct tags are the schema. `example` tags populate the sample Redoc
shows; `enums` restricts allowed values; the `validate` tag drives runtime binding
(documented via prose, since swag does not render validator rules):

```go
// CreateUserRequest is the inbound DTO for user creation.
type CreateUserRequest struct {
    Email         string `json:"email"          validate:"required,email" example:"alice@example.com"`
    QuestionLimit int    `json:"question_limit" validate:"min=0,max=200"   example:"50"`
    Status        string `json:"status"         enums:"ACTIVE,PENDING"     example:"PENDING"`
}
```

### 4.4 List / query parameters — Good

```go
// ListUsers returns a paginated list of users.
//
// @Summary      List users
// @Description  Paginated list. `page` is 0-indexed; `size` defaults to 25 and is
// @Description  capped at 100. Pagination metadata is nested inside `data`.
// @Tags         Accounts
// @ID           list-users
// @Produce      json
// @Param        page    query     int     false  "0-indexed page number"  default(0)
// @Param        size    query     int     false  "page size (max 100)"    default(25)
// @Param        status  query     string  false  "filter by status"       Enums(ACTIVE, PENDING, INACTIVE)
// @Success      200  {object}  dto.UserPageResponse  "page of users (enveloped)"
// @Failure      500  {object}  docs.ErrorEnvelope
// @Security     BearerAuth
// @Router       /users [get]
func (h *UserHandler) ListUsers(c *gin.Context) { /* ... */ }
```

`swag` does not resolve the generic `PageResponse[T]` from
`go-recipe-api-response-conventions`, so define a concrete alias struct for the docs:

```go
// UserPageResponse documents the paginated user list payload for swaggo.
// Handlers still return the generic httpx.PageResponse[dto.UserResponse].
type UserPageResponse struct {
    Page  int                `json:"page"  example:"0"`
    Size  int                `json:"size"  example:"25"`
    Total int                `json:"total" example:"142"`
    Items []dto.UserResponse `json:"items"`
}
```

### 4.5 Composite (multi-domain) response — Good

Mirror the FastAPI "composite DAO" rule: when an endpoint spans domains, document a
dedicated struct rather than an untyped map. `swag` can only render what is typed.

```go
// @Success 200 {object} dto.SummaryAndAudioResponse "summary plus optional audio"
```

```go
// SummaryAndAudioResponse is the composite payload for the regenerate endpoint.
type SummaryAndAudioResponse struct {
    Summary dto.SummaryResponse  `json:"summary"`
    Audio   *dto.AudioResponse   `json:"audio,omitempty"`
}
```

### 4.6 Streaming / binary responses — Good

For file downloads there is no JSON schema. Use `@Produce octet-stream` and a
`{file}` success type, exactly as FastAPI omitted `response_model` for streams.

```go
// DownloadAudio streams an audio file as an MP3 byte stream.
//
// @Summary      Download audio
// @Description  Streams the MP3. Clients may buffer fully or stream progressively.
// @Tags         Audio
// @ID           download-audio
// @Produce      octet-stream
// @Param        id   path   string  true  "Audio ID"
// @Success      200  {file}  binary  "audio/mpeg stream"
// @Failure      404  {object}  docs.ErrorEnvelope
// @Security     BearerAuth
// @Router       /audios/{id}/download [get]
func (h *AudioHandler) DownloadAudio(c *gin.Context) { /* ... */ }
```

### 4.7 Common annotation mistakes

```go
// Bad — no @Router: swag silently drops the endpoint from the spec.
// @Summary Get a user
func (h *UserHandler) GetUser(c *gin.Context) {}

// Bad — @Success references an unexported / unimported type; renders as {}.
// @Success 200 {object} userResponse

// Bad — duplicate @ID across two handlers: invalid spec, tools error out.
// @ID get-user   (used on two different funcs)

// Good — every handler has a unique @ID and a @Router with brace params,
// and @Success references an exported, importable struct.
```

## Section 5 — Serving Swagger UI and Redoc from Gin

`swag init` generates a `docs` package with an `init()` that registers the spec.
Import it for side effects, then mount both UIs. Keep this out of `main`'s logic —
it is wiring, so a small `registerDocs` step keeps `main` a table of contents
(`go-conventions`).

```go
package main

import (
    "net/http"

    "github.com/gin-gonic/gin"
    swaggerFiles "github.com/swaggo/files"
    ginSwagger "github.com/swaggo/gin-swagger"

    _ "github.com/example/accounts/docs" // registers the generated spec
)

// registerDocs mounts Swagger UI and Redoc against the generated OpenAPI spec.
//
// Swagger UI is served at /ac/docs/*, the raw spec at /ac/docs/doc.json, and
// Redoc at /ac/redoc. Guard this behind config so it is disabled in production
// if the API surface is internal.
func registerDocs(r *gin.Engine) {
    // Swagger UI (interactive "try it out").
    r.GET("/ac/docs/*any", ginSwagger.WrapHandler(swaggerFiles.Handler,
        ginSwagger.URL("/ac/docs/doc.json"),
    ))

    // Redoc — served as a static HTML shell pointing at the same spec JSON.
    r.GET("/ac/redoc", func(c *gin.Context) {
        c.Data(http.StatusOK, "text/html; charset=utf-8", redocHTML)
    })
}

// redocHTML is the minimal Redoc host page. The <redoc> element loads the same
// doc.json that Swagger UI serves, so both views stay in lockstep.
var redocHTML = []byte(`<!DOCTYPE html>
<html>
  <head>
    <meta charset="utf-8"/>
    <title>Accounts API — Redoc</title>
    <meta name="viewport" content="width=device-width, initial-scale=1">
  </head>
  <body>
    <redoc spec-url="/ac/docs/doc.json"></redoc>
    <script src="https://cdn.redoc.ly/redoc/latest/bundles/redoc.standalone.js"></script>
  </body>
</html>`)
```

Wiring it up in `main` (note the flat, delegated structure):

```go
func main() {
    cfg := config.Load()
    r := gin.Default()

    registerRoutes(r, cfg)
    if cfg.DocsEnabled {
        registerDocs(r)
    }

    if err := r.Run(cfg.Addr); err != nil {
        slog.Error("server exited", "err", err)
    }
}
```

Endpoints once running (analogous to the FastAPI Redoc/Swagger/openapi.json trio):

- **Swagger UI:** `http://localhost:8080/ac/docs/index.html`
- **Redoc:** `http://localhost:8080/ac/redoc`
- **Raw spec:** `http://localhost:8080/ac/docs/doc.json`

## Section 6 — Generating the spec

`swag init` is the Go analog of FastAPI generating the schema at runtime — except
you run it explicitly.

```bash
# From the module root. -g points at the file with the general API info.
swag init \
  --generalInfo cmd/server/main.go \
  --dir ./ \
  --parseDependency --parseInternal \
  --output docs

# Also emit YAML (handy for editor.swagger.io / 42Crunch):
swag init -g cmd/server/main.go --outputTypes go,json,yaml -o docs
```

Flag notes:

- `--parseDependency` / `--parseInternal` let swag resolve DTO structs that live in
  `internal/` and imported packages — omit them and cross-package `@Success` types
  render as empty objects.
- `--generalInfo` must point at the file holding the `@title`/`@BasePath` block.
- Re-run **every time** a handler annotation or a referenced DTO changes. This is
  the drift risk; Section 8 automates the check.

Add a Make target so nobody has to remember the flags:

```makefile
.PHONY: docs
docs: ## Regenerate the OpenAPI spec from swaggo annotations
	swag fmt                                   # normalize annotation formatting
	swag init -g cmd/server/main.go --parseDependency --parseInternal -o docs
```

`swag fmt` auto-aligns the annotation columns — run it before `init` so diffs stay
clean.

## Section 7 — Validating the output

Mirror the source prompt's validation gates, adapted to Go tooling.

```bash
# 1. Spec builds into the binary (generated docs are valid Go).
go build ./...

# 2. Structural validation of the JSON spec.
npx @redocly/cli lint docs/swagger.json
# or:  npx @apidevtools/swagger-cli validate docs/swagger.json

# 3. No missing $ref / empty schemas — spot-check that referenced DTOs resolved.
#    An @Success type that rendered as {} means the struct was not parsed
#    (usually a missing --parseDependency/--parseInternal or an unexported type).
```

Render test: open `docs/swagger.yaml` in the 42Crunch VS Code extension or paste
into `editor.swagger.io` to confirm it renders without errors.

## Section 8 — Keeping docs in sync in CI (drift check)

Because the spec is generated and committed, CI must fail when a PR changes
handlers/DTOs but forgets to regenerate. Pin the CLI via `tools/tools.go` so CI
uses the same version as developers:

```go
//go:build tools

// Package tools pins build-time tool dependencies so `go install` uses the
// version recorded in go.mod, keeping CI and local generation identical.
package tools

import _ "github.com/swaggo/swag/cmd/swag"
```

CI step — regenerate and fail on any diff:

```yaml
# .github/workflows/ci.yml (excerpt)
- name: Verify OpenAPI docs are up to date
  run: |
    go install github.com/swaggo/swag/cmd/swag
    swag fmt
    swag init -g cmd/server/main.go --parseDependency --parseInternal -o docs
    if ! git diff --exit-code -- docs; then
      echo "::error::docs/ is stale. Run 'make docs' and commit the result."
      exit 1
    fi
```

This is the enforcement the FastAPI setup never needed (its schema was always
live). In Go it is mandatory — a stale `docs/` package silently ships wrong
documentation.

## Checklist

Run through before merging any doc-affecting change. Each unchecked item is a
blocker.

### Annotations
- [ ] General API info block (`@title`, `@version`, `@BasePath`, `@securityDefinitions`)
      present above `main`, with `@BasePath` using the **service namespace** prefix.
- [ ] Response envelope documented once in the `@description` (Approach A) or via
      concrete wrapper structs (Approach B).
- [ ] Every handler has `@Summary`, `@Tags`, a **unique** `@ID`, and a `@Router`.
- [ ] `@Router` uses OpenAPI `{brace}` params, not Gin `:colon` params.
- [ ] `@Success`/`@Failure` reference **exported, importable** structs; error
      responses use the shared `ErrorEnvelope`.
- [ ] Request bodies documented via `@Param ... body` + a DTO with `json`/`example`
      tags; generics replaced by concrete alias structs for lists/composites.
- [ ] Streaming/binary endpoints use `@Produce octet-stream` + `{file}`.
- [ ] Protected endpoints carry `@Security`.

### Serving
- [ ] `docs` package imported for side effects; Swagger UI and Redoc mounted under
      the service namespace; docs guarded by config for production.

### Generation & CI
- [ ] `swag fmt` + `swag init` re-run; `docs/` regenerated and committed.
- [ ] `go build ./...` passes and the spec lints clean (no empty `{}` schemas).
- [ ] CI drift check regenerates and `git diff --exit-code -- docs` passes.
- [ ] CLI version pinned in `tools/tools.go`.
