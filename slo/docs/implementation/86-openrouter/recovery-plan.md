# Feature 86 — bounded architecture recovery

Date: 2026-10-02. Scope: architecture recovery only; **not Step 1 readiness, independent whole-feature review, or release approval**.

## 2026-10-02 — FIRST worker bounded topology decision

Keep production capture unchanged. Repair the immediately preceding test-lifetime blocker: the clean scenario previously enabled subreaping and allocated pipes before any cleanup boundary, then unconditionally disabled subreaping in reap. Setup script failure reproduced both wrong kernel state and leaked real descriptors. A single outer invoke boundary now owns allocated parent FDs immediately, removes explicitly closed FDs from ownership to avoid closing reused numbers, restores the captured prior subreaper value on failure, and transfers that value with successful identity for reap's finally.

This is deliberately not a new generic containment framework or a claim of complete failure cleanup. After a launcher has spawned, failure before identity still needs a finite owned descendant ledger/reap path; current writer FD admission does not prove provenance, and unmodified isolated writer children do not inherit Python monkeypatch guards. Therefore no real launcher/writer tests are rerun in this worker. Fresh behavioral proof uses real kernel subreaper state and real allocated pipes, with process creation forbidden, plus explicitly fake wait boundaries for reap failures. The first future real-process test must keep shipped writer/reporter semantics and prove exact child-local admission before every write. Raw body absence must be proved at normalization/serialization, not by extending the literal-key FD redactor into an arbitrary body scrubber.

## Decision

Keep the narrow, independent streaming capture redactor. Replace its disconnected parent-only activation with one private, one-shot FD handoff after durable workload adoption. Keep `WorkflowHandleStore` as the only durable health/admission authority. Do not build a generic capture framework, another status store, a supervisor workload wrapper, or a new scheduler preparation service.

Source-only sanitization is necessary but not sufficient for the established acceptance: `test_detached_capture_redacts_real_split_fd_writes` deliberately writes the captured synthetic key through actual inherited stdout/stderr FDs, bypassing SDK exception normalization and Python emitters. Returning to direct disk FDs would restore that demonstrated leak. Parent-only readers would regress the existing actual-parent-exit capture test. Conversely, an independent writer does not protect private history, notifier files, or scheduler artifacts; those retain their existing serialization owners.

The specs require secrecy and preservation of existing headless lifecycle, not a universal durable logging service. Capture health, activation and drain ordering are consequences of the chosen asynchronous FD interposition, **not additional F86 product features**. Finish only the lifetime needed to avoid introducing silent loss, stale health, or reordered append output. No arbitrary encoding detector, secret archive, log scrubber, crash-proof distributed transaction, or platform-lock framework.

## Present control flow: what actually breaks

1. **Launch ordering has changed since the handoff notes.** Current `launch_tool.py::_spawn_and_patch` opens two captures/receives their readiness, spawns the workload, awaits `store.write(pid=proc.pid)`, calls `_activate_capture_files`, then closes the stack in `finally`. The statement that current launch closes before PID persistence is stale.
2. **Launch activation is only in the parent.** `_activate_capture_files` reaches into `ExitStack._exit_callbacks`, mutates `_CapturePipe._completion_context`, and calls `activate`. Neither opener call supplies `completion_context`; the already-running writer consequently lacks `SLO_CAPTURE_COMPLETION`. Parent object mutation cannot update a subprocess's environment. Parent death after return therefore removes the only connected late-failure reporter. `capture_writer.py::report_failure` returns immediately without that environment entry.
3. **Immediate completion is a separate lost-health branch.** `_CapturePipe.close` observes a promptly exited writer in `_observe_writer_exit`, closes ACK, and raises fixed `OSError`. It does not call `_handle_failure`. Launch converts this into response warning text, not durable `capture_health`. Only the timeout/reaper branch calls `_handle_failure`.
4. **Resume loses ownership before adoption.** `WorkflowRelauncher.invoke` closes captures and returns only `RelaunchOutcomeDAO(pid,error,warning)`. `WorkflowCommandService._resume_locked` persists `store.relaunch(new_pid=...)` afterward. No capture lifetime or activation reaches that boundary. Premature expected-PID reporting is rejected while the reservation PID is zero; `_relaunch_sync` clears prior health when adopting the replacement.
5. **Readiness is not completion.** Fixed startup ACK precedes workload spawn, not drain success. The current completion-context test supplies context manually and tests a helper return, not actual production launch/resume activation or OS-parent-exit failure reporting. The current launch late-fault test keeps its parent alive and uses real writers with an injected failing script; its successful parent reporter does not prove independent reporting.
6. **Reservation does not drain.** `_resume_locked`'s docstring promises old capture drain, but it calls no drain operation. A per-service lock plus durable `launching,pid=0` reservation prevents the tested two-service double spawn; neither waits for the old independent append writer's final bytes. Existing independent writer sessions can outlive the old workload PID.
7. **Store authority is useful and real.** `record_capture_failure_sync` locks the existing handle, rejects a mismatched PID and atomically adds fixed degradation without changing workflow state/PID. Parent reapers now call this synchronously rather than launching a reporter subprocess. Preserve that repair. PID equality alone is not a new proof against OS PID reuse; do not advertise it as one.

Historical **173 passed** is the five-module partition recorded in the implementation log, not evidence that these disconnected paths work.

## Smallest implementable correction

### A. Explicit private lifetime, not ExitStack introspection

In `spawn_env.py`, retain explicit references to the two capture endpoints in a small private owned pair. It owns only capture FDs/process handles and close/adoption operations; it owns no durable state. Remove `_activate_capture_files`' access to `_exit_callbacks`, duck-typed private-field writes and its type-ignore. Keep `RelaunchOutcomeDAO` public and serializable; never add FDs, credentials, subprocess objects or callbacks to it.

Add a private parent→writer control pipe. Existing writer→parent readiness ACK remains fixed safe bytes. The control frame is bounded JSON containing only the existing `WorkflowCaptureCompletionContext` fields (root, owner, workflow, expected workload PID), sent once **after successful store adoption**. No key in frame/argv/durable metadata. The writer must consume this handoff independently of its input drain: drain may fail or finish before adoption. Retain that terminal result locally until activation or control EOF; never wait to read workload bytes until adoption (pipe backpressure could otherwise deadlock spawn).

The writer-side terminal path reports through the existing store authority once activated, including failures retained before activation. The parent may make an idempotent report for immediate close/control failure after adoption; both reach the same fixed store mutation. Clean EOF reports no degradation. A malformed/duplicate control message fails safely. Control EOF without adoption exits without fabricating PID-zero health. No disk spool of input or protocol state.

For relaunch, prefer a private async context-managed spawn lifetime on `WorkflowRelauncher` (e.g. `spawn_for_adoption`) that yields the workload PID and owned capture pair to the command owner. The command commits `store.relaunch`, calls pair adoption, and only then leaves the context. If compatibility needs `invoke`, make it delegate, not own a second spawn implementation. No public result exposes the private pair.

Required order for both paths:

```text
reserve/create handle
→ acquire capture admission (B)
→ open two independent redacting writers; require readiness
→ spawn actual workload (unchanged PID/process group/argv)
→ persist actual workload PID through existing store
→ send one activation to each writer; retain/report preactivation failure
→ close parent copies off the event loop; release private ownership
→ writer drains workload bytes independently of parent lifetime
→ terminal failure records fixed health through WorkflowHandleStore
```

Spawn/open failure: close/reap only owned writers, rollback the existing reservation, never invent a workload PID. Adoption failure after spawn: retain real PID and existing abort/race cleanup semantics; do not return ordinary success or replace workload identity with writer identity. Cancellation at every await must close private controls and join owned cleanup. A parent crash between spawn and durable adoption remains an existing launch-reconciliation concern, not a claim this small FD handshake makes atomic. Explicitly test and document the narrower guarantee: after successful adoption/activation, parent exit does not lose writer failure reporting.

### B. Bound the asynchronous append regression

Keep durable resume reservation. Add a narrow POSIX append-drain lease at the capture owner, not a new status file or registry: hold an advisory lock on each existing capture destination for that writer's lifetime. A replacement opener acquires the same destination lock before readiness/workload spawn. Thus old bytes are drained before a replacement workload can append its first byte. Transfer lock ownership without a release/reacquire gap; test the descriptor inheritance semantics. Close releases the lease. Use fixed stdout-then-stderr acquisition order, bounded cancellable acquisition off the event loop, and safe refusal if drain cannot complete. Do not hold the handle-store lock while waiting for writers that may need it to report.

This lease is justified only by retaining async append writers. It is not a generalized resume orchestration service. The old workload must still be rejected as live by existing process evidence. A failed old writer releases its lease after attempting fixed health publication; degraded capture cannot be represented as successful drain. Keep preexisting health evidence until replacement adoption succeeds. A separate two-OS-process test must prove the existing reservation excludes duplicate workload execution; same-loop two-service proof is insufficient.

### C. Preserve source-boundary sanitation; no capture-based substitute

Keep `OpenRouterErrorNormalizer`, safe pool audit codes, `SubAgentProcess` line sanitation, `FilesystemSessionHistoryStore` serialization protection and `WorkflowNotifier` sanitation. Centralize credential identity through the existing resolver. At each operation bind the exact effective key once for output protection; do not infer source separately or repeatedly read the mutable store for every sink. Prove old admitted key A remains protected after B becomes effective. Resolver failure must not turn a safe-output operation into raw text passthrough; fixed-safe failure is preferable to inventing a secret registry.

Opaque reasoning is not a credential: preserve it exactly in the authorized private anchor and same-route request, exclude it from public output. Never remove the extension wholesale to satisfy scans. Test literal and already-supported JSON/percent encodings separately; do not claim protection against arbitrary transformation or intentionally secret-bearing user argv inputs.
