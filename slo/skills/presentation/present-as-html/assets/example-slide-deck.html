What order does a Textual app call its methods in?

Walking the real sequence — __init__ → compose → child mount → on_mount — grounded in SloTUI.

Your model

Your four-step guess holds up

1__init__ — plain constructioncorrect
2compose — build the treecorrect
3compose on sub-componentscorrect
4on_mount — lastcorrect

One refinement. on_mount fires per widget, each child's as it finishes mounting. The app's own on_mount runs after every composed child is in the DOM — which is why it's the safe place to query them.

The signal · top to bottom

The order the source actually runs

SloTUI.__init__sync · no DOM

Registers themes, stores session, sets widget handles to None. The tree doesn't exist yet.

events.Composedispatched by run loop

The running app dispatches Compose first. This drives compose().

compose()builds & yields the tree

Each yield constructs a child (its __init__ runs now) and hands it off to mount.

↳ recurse — every child repeats the cycle: its compose, its children, then its on_mount. Children mount before the parent's mount completes.
child.on_mount × Nleaf-first as compose unwinds

Each child posts its own Mount as it lands in the DOM — resolving before the app's.

events.Mount → SloTUI.on_mounttree is live & queryable

Dispatched only after the subtree is mounted. Now self._input & friends are real widgets.

Source proof

Compose is dispatched before Mount

The order is fixed in App._process_messages — on_mount always runs after the tree is built.

textual/app.py · run_process_messages() · ~L3073
# the app's own mount sequence, in order:
await self._dispatch_message(events.Compose())   # → compose() builds children
await self._dispatch_message(events.Resize.from_dimensions(...))
self.stylesheet.apply(self)
await self._dispatch_message(events.Mount())     # → on_mount() runs last

Takeaway: compose builds the tree; on_mount fires per-widget once that widget — and its subtree — is in the DOM.

Inside on_mount() — order is load-bearing

1_hydrate_transcript_from_history()Replay persisted events into the same widgets a live run uses.
2_maybe_render_startup_notice()One-time tip line for new sessions.
3session.subscribe(handler=…)Subscribe the live renderer — strictly after hydration.
4self._input.focus()Hand the user a ready cursor.
5push AuthenticationScreen if no credentialBlock input until the active model can authenticate.

Why 1 before 3 (sub-spec 05.e §7.2): hydrate the replay tail before subscribing live events, so a fresh prompt's events can't interleave with historical ones.

The reliable rule

Remember this, forget the rest

__init__ stores config · compose builds the tree · on_mount fires per-widget once it's in the DOM — children first, the app last. Query and wire up only in on_mount.
