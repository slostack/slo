# Slo Skills Index

This file lists the skills available to the slo agent. The agent reads this
index on demand (via the `read` tool) when a task starts; when a task matches
a skill's description and routing hints, the agent then reads that skill's
`SKILL.md` and follows its instructions.

Each skill below is a markdown file with YAML frontmatter (`name`,
`description`, `when_to_use`, `group`, `kind`) plus an instructional body.
The index is grouped into **Workflows** and **Individual Skills**, then
split by category.

> **Note:** this file is regenerated by `make build-skill-index` from the
> committed `skills/<group>/<slug>/SKILL.md` tree. Edit the SKILL.md files
> (not this index) when adding or revising a skill, then re-run the
> regenerator.

### Design and Analysis
- **breakdown-feature-spec-to-tasks** — Decomposing an approved Confluence/feature spec into JIRA sub-tasks with dependencies. When to use: Use when a spec is signed off and you need to slice it into actionable, ordered tasks. Path: `skills/design-and-analysis/breakdown-feature-spec-to-tasks/SKILL.md`
- **code-test-review** — Pipeline workflow for turning a specification or task slice into tested code, structured review findings, and a completion assessment. When to use: Use when the user explicitly asks to implement a spec, build a planned task, or take a verified feature slice from specification to tested code. Path: `skills/design-and-analysis/code-test-review/SKILL.md`
- **development-reviews** — The two-agent review handshake protocol (.agent_discussions.md turns). When to use: Use whenever participating in the coding-agent / review-agent loop. Path: `skills/design-and-analysis/development-reviews/SKILL.md`
- **distill-learnings** — End-of-implementation: capture non-obvious solutions and patterns to LEARNINGS.md. When to use: Use at the close of a session where something hard was figured out. Path: `skills/design-and-analysis/distill-learnings/SKILL.md`
- **feature-specification-verification** — Reviewing a draft spec for gaps and ambiguities before implementation begins. When to use: Use as a post-hook after writing a spec — surfaces missing decisions, underspecified edge cases, and inconsistent acceptance criteria. Path: `skills/design-and-analysis/feature-specification-verification/SKILL.md`
- **feature-specifications** — Style guide for writing technical feature specifications. When to use: Use when authoring a spec from scratch — covers structure, scope, acceptance criteria, sequencing. Default workflow: load feature-specifications-pre-hook first (pre-hook), then this, then feature-specifications-post-hook (post-hook). The older gather-feature-context and feature-specification-verification skills remain available as legacy companions when explicitly requested. Path: `skills/design-and-analysis/feature-specifications/SKILL.md`
- **feature-specifications-post-hook** — Self-review pass that runs after a feature specification is drafted with feature-specifications. Catches gaps, convention drift, oversized scope, weak examples, spec-mode mismatches, and missing test coverage before the spec is handed to a developer or published. When to use: Use as the mandatory post-hook for feature-specifications. Path: `skills/design-and-analysis/feature-specifications-post-hook/SKILL.md`
- **feature-specifications-pre-hook** — Context-gathering pass that runs before drafting or revising a feature specification with feature-specifications. Loads KB, MEMORY.md, repo guardrails (CLAUDE.md / AGENTS.md / docs/RESEARCH.md), code conventions, and the current state of the affected surface so the resulting spec respects existing patterns. When to use: Use as the mandatory pre-hook for feature-specifications. Path: `skills/design-and-analysis/feature-specifications-pre-hook/SKILL.md`
- **gather-feature-context** — Pre-hook for feature-specifications: pulls together domain, business, current-state, and implementation context (JIRA, Confluence RFCs/PRDs, Google Drive, KB, memory, external sources) into a sign-off briefing before spec writing starts. When to use: Use before drafting a feature specification when you need a sign-off-ready bundle of business, architecture, code, and KB context. Path: `skills/design-and-analysis/gather-feature-context/SKILL.md`
- **headless-orchestration** — Launch a named Slo workflow in headless mode — triggered by an explicit detach qualifier ("headless" / "detached" / "independent" dynamic workflows, or a named workflow with detach wording), not by an unqualified "dynamic workflows" request (which runs in-session via spawn_sub_agents). Sets the required timeout env vars, selects models per phase, dispatches phases serially or in parallel, and monitors child agents until the orchestrator reaches a terminal state. When to use: Use when the user explicitly asks to run a workflow headlessly with a detach qualifier ("headless dynamic workflows", "detached dynamic workflows", "independent dynamic workflows", "run the code-test-review workflow detached"), or says "in the background" / "without blocking" applied to a workflow request. An unqualified "dynamic workflows" or "dyanmic workflows" phrase (no detach qualifier) does NOT trigger this skill — that runs in-session via spawn_sub_agents. Path: `skills/design-and-analysis/headless-orchestration/SKILL.md`
- **implement-feature-request** — End-to-end workflow for turning a feature request or JIRA story into specs, code, tests, review, and documentation updates. When to use: Use when the user asks for implementation of a feature request, JIRA story, or request.md artifact rather than a narrow one-off code change. Path: `skills/design-and-analysis/implement-feature-request/SKILL.md`
- **orchestrator** — Gateway workflow that decides which skill or workflow to load next for the current task. Routes "dynamic workflows" / "dyanmic workflows" (no detach qualifier) to in-session multi-agent orchestration via spawn_sub_agents; routes a detach-qualified request ("headless dynamic workflows", "detached dynamic workflows", "independent dynamic workflows", or a named workflow with "in the background" / "without blocking") to the headless-orchestration skill. When to use: Use at the start or end of a turn when you need to route the task into the right Slo workflow, category, or individual skill. Path: `skills/design-and-analysis/orchestrator/SKILL.md`
- **review-feature-code** — Reviewing a feature implementation against its spec. When to use: Use as a structured pre-landing review for a feature PR. Path: `skills/design-and-analysis/review-feature-code/SKILL.md`
- **specification-development** — Pipeline workflow for taking a feature brief through context gathering, spec drafting, verification, and dependency-ordered task breakdown. When to use: Use when the user explicitly asks to write, spec out, plan, or break down a feature specification from a brief, ticket, RFC, or feature request. Path: `skills/design-and-analysis/specification-development/SKILL.md`
- **update-documentation-after-code-changes** — After any non-trivial change — update docs/RESEARCH.md and code-prompts as needed. When to use: Use post-merge or after a significant feature lands. Path: `skills/design-and-analysis/update-documentation-after-code-changes/SKILL.md`
- **update-knowledge-base** — At session end — incrementally update the Obsidian KB with insights, decisions, and gotchas. When to use: Use when you've learned something non-obvious that future sessions need. Path: `skills/design-and-analysis/update-knowledge-base/SKILL.md`
