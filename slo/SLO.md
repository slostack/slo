# Slo Repo Conventions

- Read `AGENTS.md` first for any code, architecture, workflow, or testing task in this repository.
- If the user says **"dynamic workflows"** or the misspelling **"dyanmic workflows"**, treat that as an explicit request to use the orchestrator / headless workflow path: launch a Slo orchestrator that launches multiple Slo agents to execute the workflow's parts.
- Outside that shorthand, preserve the normal policy: only use orchestrator / `spawn_sub_agents` execution when the user explicitly asks for it.
- **Orchestrator timeouts for slow-test projects:** `spawn_sub_agents` blocks the orchestrator's own stream while a child runs, so the parent guard `SLO_STREAM_INACTIVITY_TIMEOUT_SECONDS` (default `4800`) — not the child's `SLO_SUBAGENT_INACTIVITY_TIMEOUT_SECONDS` (default `3600`) — is the real ceiling on a single blocking phase, and a continuously busy child never trips its own guard. When a phase's gates run long (e.g. `go test -race ./...`) the orchestrator falsely aborts with `TimeoutError: main agent stream produced no events ...; treated as hung`. For such projects the optimal values are `SLO_STREAM_INACTIVITY_TIMEOUT_SECONDS=10800` and `SLO_SUBAGENT_INACTIVITY_TIMEOUT_SECONDS=7200` (keep parent > child); export them before starting the orchestrator, and prefer splitting phases. See `AGENTS.md` and KB `slo/headless-workflow-orchestration.md`.
